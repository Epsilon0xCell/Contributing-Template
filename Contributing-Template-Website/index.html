Contributing-Template: The Annotated Blank

I keep this repository for one file: CONTRIBUTING.md, a ready to copy contributing guide generated with generator.contributing.md. An adopter copies it into another project and fills in the slots. On this page I show it the way an adopter meets it, as a ruled form with every slot and TODO marked in my margin, and nothing filled in with invented details.

How to read this pageThe left column is the guide itself, section by section, in the order its own table of contents gives. The yellow margin is me. If a line is blank, I left it blank, because the template leaves it blank.

The form, section by section

I checked the table of contents against the headings in the file. All ten anchors resolve to sections that exist. Here they are, in that order.

The project and everyone in it is governed by the project code of conduct, and unacceptable behavior is reported to the project maintainer. My capture below shows the exact wording.

Fixed in an earlier pass, and I want it visible: this section used to link to a CODE_OF_CONDUCT.md file this repo does not contain. It now says so plainly. See capture 1.
Section 02

I Have a Question

Written in full

Read the README first, search existing issues, then open an issue with as much context as you can give.

Watch the links here. This section points at /issues and /issues/new, which do not land where an adopter expects. I explain that under its own heading below.
Section 03

I Want To Contribute

Written in full

The umbrella section, opening with a legal notice: by contributing, you agree you authored the content and hold the rights to it.

Reporting Bugs and Suggesting Enhancements sit under this heading in the file, and the table of contents lists them on their own. I follow the contents list, so they get their own rows next.
Section 04

Reporting Bugs

Written in full

Before submitting: confirm the latest version, check the bug tracker, collect a stack trace and version details. Submitting: open an issue, describe expected and actual behavior, give reproduction steps.

The security line in this section is where the second maintainer passage lives. Sensitive bugs go by email to the project maintainer, never to the public tracker. See capture 3.
Section 05

Suggesting Enhancements

Written in full

Search first, then open an issue with a clear title, a step by step description, the current behavior, the behavior you expected, and why it would help most users.

This section also links out through /issues, so the same adopter warning applies.

The /issues quirk, in my margin

The question, bug, and enhancement sections link to root relative /issues and /issues/new paths, as the generator wrote them. On GitHub those resolve against the github.com root, the signed in reader's own issue pages, rather than against the adopting repository. If you adopt this guide, replace them with your project's own issue URLs. I documented the quirk instead of rewriting it in the template, because the right target is the adopting project's address, which this template cannot know.

Credit and adoption

The guide was generated with generator.contributing.md, and its own attribution line in the file credits the contributing-gen project. To adopt it: copy CONTRIBUTING.md into your project, add a CODE_OF_CONDUCT.md, replace the /issues links with your own issue URLs, point the documentation links at your own documentation, and fill in the four TODO blanks. Until then, the blanks stay blank, including on this page.
